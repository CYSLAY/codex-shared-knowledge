# 用 Codex + Stitch 做高质量前端效果

## 核心摘要

视频把前端制作拆成“设计”和“工程实现”两类问题，并给出一条五步工作流：先确定视觉方向，再让 Codex 形成页面与模块级 PRD，用 Google Stitch 生成并迭代可视原型，通过 Stitch MCP 把设计资产交给编码代理，最后由 Codex 补齐交互与业务逻辑。真正可复用的是“需求—设计—实现分层”和中间交付物，不是照抄某个案例。

## 完整内容时间轴

- `00:00–00:22`：对比“功能可用但 AI 味明显”的页面与更完整的设计效果，提出教程目标。
- `00:22–00:48`：解释页面由设计与工程两部分组成。颜色、字体、间距和版式属于设计；表单、状态管理和数据请求属于工程。视频认为 Codex 更擅长后者，因此需要设计工具补位。
- `00:48–01:13`：在 Dribbble 等案例站观察风格，选择极简、瑞士风、暗黑科技等方向；强调不是直接复制案例，而是确定适合当前产品的视觉方向。
- `01:13–01:58`：先让 Codex 输出前端需求文档，不急于写代码。文档应明确页面、页面内模块及模块功能，并形成可复用的 Markdown PRD。
- `01:58–02:40`：把 PRD 与风格参考图交给 Google Stitch，生成第一版界面原型。画面显示当前模型选择项；模型名称随产品更新，不作为稳定工作流条件。
- `02:40–02:58`：在 Stitch 内通过自然语言继续修改局部设计，例如删除不需要的装饰边条。
- `02:58–03:51`：从 Stitch 导出入口选择 MCP，配置 Stitch MCP，再利用项目/画面的标题和 ID 让编码代理取得设计资产。视频画面涉及认证配置，但本笔记不记录、复述或保存任何密钥。
- `03:51–04:15`：要求 Codex 严格参考 Stitch 原型和 PRD，做高保真前端实现。
- `04:15–04:49`：在已有设计规范和框架上继续补齐点击状态、交互和业务逻辑，并迭代不理想的视觉细节。
- `04:49–05:01`：总结并介绍作者的知识库与配套 Skill，随后结束。

## 官方资料核验

- Google 官方介绍：<https://developers.googleblog.com/en/stitch-a-new-way-to-design-uis/>。Stitch 是 Google Labs 的实验性 UI/UX 设计与前端代码生成工具，支持自然语言、图片或线框图输入、对话式迭代、Figma 交接和前端代码导出。
- Google Cloud 官方 MCP 列表：<https://docs.cloud.google.com/mcp/supported-products>。截至处理日，Stitch MCP 标记为 Beta，官方端点为 `https://stitch.googleapis.com/mcp`。
- Google 官方 Gemini CLI 扩展：<https://github.com/gemini-cli-extensions/stitch>。官方文档确认可列举项目/画面、生成画面并下载 HTML 与图片；认证可使用 Stitch API Key 或 Google Cloud ADC。API Key、Cloud Project、IAM 权限属于敏感配置，不应写入提示词档案、聊天记录或知识库。
- 适用：视觉目标尚不清晰、需要先出多版 UI 原型、设计与开发需要可追踪交接、已有 PRD 但缺少视觉方案的前端任务。
- 不适用：已有成熟设计系统和完整设计稿、只修复逻辑 Bug、不能把内容提交给外部云服务、或无法接受 Beta 接口变化的任务。
- 来源环境状态：有 `design-taste-frontend`，但未配置 Stitch MCP。接收者应检查自身环境；若用户要求接入，先确认数据边界和授权，再以安全方式配置认证，不能复制视频画面中的密钥。

## 可复用工作流

1. 写清业务目标、用户和关键流程。
2. 选择视觉方向并记录可执行的设计约束，而非只贴“高级感”参考图。
3. 形成页面—模块—功能—状态—数据的 Markdown PRD。
4. 用设计工具生成原型并完成视觉迭代，冻结稳定的项目/画面标识。
5. 通过官方导出或 MCP 取得 HTML、截图和资产；密钥只放在安全配置中。
6. 由编码代理实现交互与业务逻辑，最后用浏览器做同视口视觉、状态、响应式和可访问性验收。
