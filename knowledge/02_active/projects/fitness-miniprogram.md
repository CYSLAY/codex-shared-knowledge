# 健身小程序

## 项目目标

原生微信小程序，用于训练计时、动作与组数记录、身体数据、日历统计和肌群反馈。核心要求是离线可用、多设备同步时不丢记录，以及用户可恢复误操作或错误同步前的数据。

## 核心架构

- 微信身份与 OpenID 隔离用户数据。
- 本地存储为第一数据源；离线时继续记录，恢复网络或回到前台后自动同步。
- 云端使用当前快照表与历史版本表；每次有效写入同时保存同步前、同步后快照。
- 客户端和云函数各自实现同一套快照合并逻辑，并用测试保持一致。

## 同步协议

- 训练记录以 `id`、身体数据以日期或 `id` 为键，冲突时选择 `updatedAt` 更新的一方。
- 删除不是“数组里消失”，而是带 `deletedAt` 的 tombstone；只有删除时间不早于记录更新时间才真正移除。
- 空本地快照与云端合并，不能直接覆盖云端；没有明确 tombstone 时，训练和身体记录数量不允许减少。
- 云端写入前执行无意外丢数保护；任何无删除标记的记录减少都会阻断事务。
- 快照先规范排序后生成 fingerprint；内容未变化则跳过写入和历史版本，减少无意义版本膨胀。
- 云函数暴露能力握手。客户端确认服务端具备兼容旧数据、历史恢复、防丢数和跳过重复写入能力后，才允许上传。
- 本地状态在同步期间再次变化时，不把旧同步结果标记为最终完成，而是安排下一轮推送。

## 恢复机制

- 历史列表同时展示每次同步前与同步后版本。
- 恢复时为被恢复记录刷新 `updatedAt`，并清理与这些记录冲突的 tombstone，再通过正常合并与事务写回。
- 删除集合、批量改结构或升级同步逻辑前，先导出云端集合并完成恢复演练。

## 产品细节

- 训练时长基于真实开始时间计算，即使退出小程序也能恢复；异常长计时需提示人工校正。
- 有氧项目可记录自身分钟数，但不重复计入整体训练时长。
- 动作映射到肌群热力图；支持自定义动作、不同性别主题和身体数据趋势。
- 高风险删除使用强确认，并保留可恢复历史。

## 可复用经验

1. 多设备本地优先同步不能依靠“最后上传的整包覆盖”，应采用逐记录合并、删除墓碑和版本时间。
2. 客户端升级依赖新服务端能力时，应先部署服务端，再通过能力握手放行客户端写入。
3. “不丢数据”应成为代码断言和事务门禁，而不是发布说明里的愿望。
4. 每次同步保留 before/after 快照，才能同时支持审计、定位和用户自助恢复。
5. UI 更新与数据协议更新应采用不同发布流程；只有后者需要备份、能力验证和恢复演练。

## 发布红线

- 不得在旧云函数仍在线时先发布依赖新同步协议的客户端。
- 不得删除生产集合或用空数组代表删除。
- 不得在没有备份和恢复演练时执行批量迁移。
