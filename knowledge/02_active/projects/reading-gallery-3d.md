# 3D 阅读档案网站

## 项目结论

把个人阅读记录做成独立部署的电影化 3D 浏览体验。最终方案不是浏览器实时建模，而是以 13 秒预渲染写实视频承担空间、镜头和高成本 3D 细节，再由 React、GSAP 和网页前景层负责 Loading、时间映射、单书介绍、终场文字、全部书目及笔记交互。

项目独立部署到 `reading-archive-3d`，不修改、不覆盖原 `reading-gallery` 网站。这一隔离原则从立项到发布始终保留，是本项目最重要的风险控制之一。

## 用户明确确认的视觉叙事

### 从最初构想到最终成片

- 最初设想是机械门进入书库、圆盘近景、3 本书展示、最后进入大型书库。
- 用户认为前段铺垫太长，要求尽快进入“书”的核心画面；叙事重心因此从展示空间改为展示阅读内容。
- 3 本书的呈现被否定：排布缺乏冲击力。中间一度改为多本书飞起、在空中打开、强化大透视，最终网站的重点信息层收敛为 1 本近期读书笔记，降低网页信息与复杂视频画面的竞争。
- 圆盘必须具有明确的机械旋转感，不能只作为静态布景；但后续 Kling 成片结构变化后，圆盘不再承担网页内容展示主轴。
- 终场不能突然切换到新空间。镜头必须沿当前场景继续推进，直到圆盘自然离开视野，最终定格为当前书库背景中“一大片书架的正视图”。空间连续性优先于单张画面的宏大感。

### 时间静止的世界规则

用户反复强调“整个空间处于时间静止状态”，因此视觉元素必须共享同一物理规则：

- 多本漂浮且打开的书、纸张、机械臂、小型无人机、工具箱和散落工具全部被冻结在空中。
- 烟雾也必须静止，不能因烟在流动而破坏定格世界的可信度。
- 动的是镜头，不是场景物体；镜头要有大范围旋转、穿行和掠过，不能只有平直前推。
- 镜头先进入场景，快速抵达一本已打开的书做特写，再掠过各种 3D 物品，最后抵达同一场景中的大型书架。

可复用规则：概念片一旦确立世界物理规则，所有粒子、烟、纸张和机械装置都要服从它；局部“更生动”的运动反而可能成为穿帮。

## 最终网站时间轴

| 阶段 | 最终行为 | 用户反馈来源 |
|---|---|---|
| Loading | 全黑背景，只保留机械密码锁；数字从 0 平滑增长到 100，即使资源已加载也要保留可感知的增长过程 | 门与背景素材难以和视频第一帧无缝对齐，最终删去开门方案 |
| 解锁 | 到 100 时，锁右侧产生少量红橙色电线短路火花，右侧快速下倾，使整体约呈 30°，随后像失去固定一样自由落下；黑幕渐隐露出视频 | 用户指定故障式机械反馈，不要普通淡出 |
| 视频前段 | 尽快进入书的画面，减少空间铺垫 | 初版视频前段过长 |
| 单书介绍 | 只展示最新 1 本；标题翻译成英文，同时保留中文书名、作者、摘要和完整笔记入口；介绍要比原先更早出现，并在镜头离开该书时及时消失 | 用户认为 3 本书分散注意力，且第一本信息出现、消失都太晚 |
| 过渡段 | 网页使用内容感知的非线性时间映射：延长书的可读时间，压缩工具箱拖沓段 | 成片无法重生成，只能在网站时间控制层补救节奏 |
| 最后 1.5 秒 | “所有读过的书都在这里”等终场引导文字开始出现 | 文字属于视频尾声，而不是书卡阶段 |
| 视频结束后 | 全部书卡自动、不规则、分块陆续出现，整个过程 1 秒内完成，不要求继续下滑 | 用户多轮纠正：必须等视频结束、必须自动、必须 1 秒完成 |
| 全部出现后 | 才启用书架上下滚动和卡片交互，避免视频滚动、书架滚动互相抢事件 | 用户明确要求交互门控 |
| 反向离开终帧 | 全部书目渐隐消失，不能持续覆盖退回的视频画面 | 用户发现回滚时档案层一直挡住画面 |

## 开场方案的演进与取舍

### 被放弃的机械门方案

最初计划把视频第一帧拆成左右两扇透明机械门，网页加载完成后水平打开，再与视频第一帧对齐并渐隐。实际遇到的问题：

- 只有门的透明素材无法补齐门框、墙体和周边环境，Loading 背景出现大量穿帮。
- 静态参考图与视频第一帧在透视、亮度、压缩纹理和构图边界上难以像素级匹配。
- 网页门的位移、消失时机和视频内部镜头运动叠加，产生“开了两次门”或画面跳变感。
- Loading 后提前露出全部书画面，破坏后续叙事。

最终选择全黑 Loading + 单独密码锁 + 黑幕渐隐。这个方案牺牲了“门的戏剧性”，但显著提高衔接可靠性，也让观众把注意力留给正式视频。

### 可复用判断

若网页前景必须与视频第一帧无缝拼接，不能只验证单张素材好不好看，必须预先做三项测试：首帧像素对齐、动画结束帧对齐、压缩后颜色/黑位对齐。如果无法同时通过，应改用全黑、雾化、闪白等可容错的转场，而不是继续堆补丁。

## 单书信息层的设计经验

- 用户最终偏好 1 本书而不是 3 本：电影镜头已经复杂，网页前景需要单一焦点。
- 最新记录自动成为主角书，不在代码中手工固定，保证原站更新后内容自然前移。
- 第一本书标题翻译成英文以获得更强的视觉字形和电影海报感，同时保留中文标题以避免信息损失。
- 信息的出现不能只按总进度粗略估算，要逐帧对照“书进入可读构图”和“镜头开始离开书”的画面锚点。
- 特写层一旦挡住用户开始关注的新空间，就算文字仍可读也应该退出；内容相关性比停留时长更重要。

## 终场全部书目的交互经验

终场经历了多轮纠正，最终形成严格的状态顺序：

`尾声文字出现 → 视频抵达最后一帧 → 书卡自动在 1 秒内不规则出现 → 全部完成 → 开放内部滚动与点击`

- 书卡不能在最后 1.5 秒和视频争夺注意力；这段只出现引导文字。
- 书卡出现不依赖用户再滚动，否则用户容易误以为页面卡住。
- 不规则分块顺序比统一从上到下更像档案系统被逐块唤醒。
- 动画期间 `overflow-y: hidden`、`pointer-events: none`；完成后再切为可滚动、可交互。
- 用户反向滚动离开终帧时，档案层要渐隐并关闭交互，恢复对视频的观看。

## 桌面端与移动端不是同一种交互

### 桌面端

- 鼠标滚轮通过 GSAP ScrollTrigger scrub 控制视频时间。
- 使用分段非线性映射，不让页面滚动距离与视频秒数线性对应。
- 书的特写区分配更多滚动距离，工具箱等无核心信息片段被压缩。

### 移动端

- 初版“点击一次后自动继续”被用户纠正为“按住行进，松开停止”。这更接近用户对镜头推进的身体控制，也避免误触后无法停下。
- 按住期间使用视频原生连续播放，并通过 `requestVideoFrameCallback` 反向同步页面进度；比高频给 `currentTime` 赋值更流畅。
- 整体行程必须与成片一致，约 13 秒，不能因为网页映射导致移动端显得明显更慢。
- 控件和说明文字禁用长按选词、系统呼出菜单和点击高亮：`user-select: none`、`-webkit-touch-callout: none`、`touch-action: none`。搜索框等真正需要编辑的区域单独恢复文本选择。
- 移动端需要独立码率版本，不能只把桌面大文件缩放显示。

## 媒体加载与画质策略

### 已采用方案

- 保持 13 秒、1920×1080、24 fps 和原始构图。
- 桌面版约 24 Mbps，最大关键帧间隔 8 帧；移动版约 12.5 Mbps，最大关键帧间隔 12 帧。
- 网站综合视口、粗指针、Save-Data 和网络类型选择媒体。
- 视频后期使用稳定的逐帧降噪、局部对比、亮度锐化，以及带羽化的右下角局部修补来去除“视频由 AI 生成”字样，不通过粗暴裁剪破坏构图。
- 更密关键帧主要改善频繁 seek 的响应和稳定性，不会真正恢复 AI 生成时已经丢失的细节。清晰度增强应处理视频帧序列，而不是只改编码参数。
- Loading 以真实视频缓冲为目标值，但显示层用匀速追赶，避免资源瞬间就绪时数字从 0 跳到 100。

### 重要陷阱

- 大文件会明显影响首次加载。40 MB 级桌面视频可以换来更清晰的画面，但必须配合安全初始缓冲、移动版资源和 Range 请求。
- “等整个视频下载完再开门”会让 Loading 过长；“只看计时器不看资源”又可能进入后黑屏。正确门槛是达到可安全开始播放的缓冲量。
- 移动 Safari、低数据模式或浏览器节能策略可能拒绝自动预加载。Loading 状态机不能无限等待 `buffered` 或一次性 fallback；必须有二级超时、重试或明确的用户手势入口。
- GitHub Pages URL 上的 `?release=<commit>` 只是查询参数，不会把页面固定到那个提交。资产版本应依赖构建 hash 或真实发布版本，不能把查询参数误当回滚机制。

## 数据同步经验

- 原阅读网站是内容源，3D 网站只读取最新信息，不反向修改原站。
- 抽取脚本解析书架、弹窗元数据、标签、摘要、完整 HTML 笔记和封面地址，输出结构化 `books.json`。
- 必须兼容旧版笔记直接位于弹窗容器和新版 `.modal-body` 包装两种 DOM，否则历史书籍会被错误显示为“真正归档”或无正文。
- 所有读过的书都应进入最终档案，不只同步近期书目；最新一本仅用于单书主展示。
- 用户自己的封面/图片可以读取，但在电影画面中可不展示，避免破坏统一的写实工业视觉。

## 做得好的部分

1. **技术路线克制。** 用成片承载写实 3D，用网页承载交互和文字，避免实时 WebGL 在移动端的性能风险。
2. **允许网页重剪视频节奏。** 无法重生成成片时，非线性时间映射有效延长书的特写、压缩工具箱段。
3. **持续保护原站。** 从数据读取到 GitHub Pages 部署始终使用独立项目和路径。
4. **反馈转化为状态机。** 终场文字、视频结束、书卡动画、滚动解锁和反向隐藏被拆成明确状态，不再靠单个滚动进度混在一起。
5. **移动端重做输入模型。** 采用按住前进、松开停止，并使用原生播放路径解决频繁 seek 卡顿。
6. **画质与性能分设备处理。** 没有只做一份超大视频，而是建立桌面/移动资源和安全缓冲门槛。
7. **真实内容驱动。** 最新书自动成为主角，全部历史笔记进入终场档案，视觉体验没有脱离原阅读数据。

## 踩过的坑与根因

1. **AI 一次生成完整长镜头不等于一次满足叙事。** 前段过长、书段过快、工具箱拖沓、终场空间不连续，说明提示词只能约束意图，不能代替逐段节奏和镜头连续性验收。
2. **参考图之间缺少空间连续性。** 最后一张换成新书库，会诱导模型生成新空间；终帧必须从同一场景、同一书架、同一光照继续推进。
3. **多主体与网页信息争夺注意力。** 3 本书和复杂漂浮场景叠加后焦点分散，最后收敛到 1 本更有效。
4. **透明门素材不是完整场景。** 缺少门框和周边背景会穿帮，且很难与压缩视频首帧无缝对齐。
5. **时间点只凭秒数容易失准。** 必须以实际画面锚点标注信息层的进出，而不是只说“第 6 秒左右”。
6. **终场交互过早开放会冲突。** 视频滚动、页面滚动、书架内部滚动和卡片点击必须分阶段解锁。
7. **移动端频繁 seek 会卡。** 按住时使用原生播放，只有桌面 scrub 或必要同步时才修改 `currentTime`。
8. **长按默认行为会破坏沉浸。** 必须在移动控件、说明文字、书卡区域禁用选词和系统菜单，同时保留输入框可选择。
9. **加载进度太真实也可能不好看。** 真实资源瞬间完成时仍需显示层平滑增长；但显示动画不能脱离资源安全状态。
10. **工具能力缺失不能只宣布降级。** 本项目后续排查中，Agent Reach 多次被当成“不可用”而未主动修复。正确流程应是检查命令、PATH、安装完整性和 Python 兼容性，在用户目录可安全修复时直接修复并运行 `doctor`；只有系统级变更或登录凭证才请求用户。

## 下一次同类项目的前置验收门

### AI 视频生成前

- 用 5—7 张关键帧建立同一空间的连续坐标、光线和物体关系。
- 对每一段写明：镜头位置、镜头运动、场景中哪些物体必须静止、目标时长、进出画面锚点。
- 首先验证核心主体出现时间，避免把大部分时长消耗在建立场景。
- 终帧必须从倒数第二帧自然推演，不单独设计一张更宏大的新空间。

### 网站接入前

- 导出视频时间码表，标出书特写开始/结束、尾声文字开始和最终静帧。
- 同时产出桌面版、移动版、首帧 poster 和兼容 fallback。
- 测试 Loading 最快网络、慢网、缓存命中、无缓存、Save-Data、Safari 禁止预载六种状态。
- 测试正向滚动、反向滚动、快速甩动、按住/松开、触控取消、旋转屏幕和页面恢复。

### 发布前

- 验证原站仓库与部署配置完全未改动。
- 验证全部历史笔记正文、最新一本排序、空字段和旧 DOM 数据。
- 真机检查移动端帧率、内存、初始加载、长按选词和内部滚动解锁。
- 使用线上实际 URL 验收，不把查询参数当成版本固定或发布成功证据。

## 当前边界

- 3D 画面是预渲染媒体，不是可自由漫游的实时三维场景。
- 书目更新仍需重新运行抽取脚本并发布生成数据。
- 后期锐化只能提升感知清晰度，不能重建 AI 原视频不存在的真实纹理。
- 移动浏览器对媒体预载的限制仍需通过有界 fallback 和用户手势策略持续防护。
