# CEC 客户看板

## 项目目标

保险顾问的客户经营工作台，把零散沟通逐步沉淀为客户档案、关键事实、顾问判断、待验证问题、下一步动作、提醒和重要日期。产品当前以本地运行版本为权威，不再把在线版本视为最新交付。

## 产品结构

- 当前完成重点是潜在客户中心；已保客户模块尚未完整建设。
- 核心实体为客户、沟通、提醒和重要日期。
- 新建客户只要求姓名，先生成稳定客户编号与标准 KYC 骨架，其余信息后续渐进补充。
- 重要日期与普通跟进提醒视觉分层；日期不确定时显示“待补”，不猜测。
- 移除了沟通方式、顾问头像、阶段打分等低价值字段，优先保留真正影响下一步行动的信息。

## GPT/MCP 协作模式

- 页面保留完整沟通原文；GPT 将原文拆为摘要、事实、档案更新、需求、顾虑、判断、待验证问题、下一步动作和提醒。
- 原始事实、客户原话、顾问判断与未验证假设必须分层，推断不得覆盖事实。
- 任何写回都先向用户展示摘要并获得确认。
- MCP 工具明确标记只读/写入/破坏性属性，并要求先确认客户身份再读取或写入。
- 新增信息采用追加或有证据的更新，不用一次 AI 总结覆盖整份历史档案。

## 技术与数据

- Next/vinext + React + Drizzle + SQLite/D1 形态；本地数据位于 `.wrangler`。
- 基础客户档案与本地新增客户分开加载；动态记录进入本地数据库。
- 沟通表同时保存 `rawNote` 与结构化结果，便于回溯 AI 的整理依据。
- MCP 使用 Streamable HTTP JSON-RPC，提供客户、沟通和提醒相关工具。

## 可复用经验

1. AI 进入 CRM 时，必须保存原文，并显式区分事实、引用、判断和假设。
2. 用户确认应位于结构化结果写回之前；“模型能生成”不等于“模型可直接改档案”。
3. 客户档案适合渐进式建模：先稳定身份和空骨架，再随证据补充，而不是首次建档强迫填满。
4. 外部集成应先验证底层需求。若页面内日历已满足需求，就不必先扩张到 iOS 同步。
5. 业务验收应采用真实工作流，旧的模板测试或启动页测试不能证明产品完成。
6. 打包 SQLite 前要停止服务并处理 WAL；测试数据应有明确前缀并在交付前清理、核对记录数。

## 完成状态的表达

- 代码完成、构建完成、部署完成和业务验收完成是四种不同状态。
- localhost 可用不能表述为线上可用。
- 账号属于某工作区，不代表其天然拥有源代码仓库权限。

## 当前边界

- 当前权威版本仅本地使用；两台 Mac 之间没有自动合并。
- 已保客户模块、重要日期编辑/删除/导入仍待完善。
- 知识库只沉淀产品与工程方法，不复制真实客户姓名、联系方式、沟通正文或其他个人信息。
