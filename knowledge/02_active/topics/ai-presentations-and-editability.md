# AI 演示文稿的可编辑性与职场验收

## 当前认识

AI 能生成“看起来像 PPT”的画面，不等于已经进入真实演示文稿工作流。职场可用性至少包含原生编辑、复杂逻辑排版、品牌模板一致性和可靠导出。

## 建议验收维度

1. 文件真实性：交付物是否为可正常打开的 PPTX，而不是图片、视频或网页伪装。
2. 元素可编辑：文字、形状、图片、图表和连接线能否分别选择、修改和移动。
3. 结构表达：流程、时间线、矩阵、组织关系和复杂逻辑图是否清楚、稳定。
4. 模板一致性：是否能继承公司字体、颜色、母版、页眉页脚和组件规则。
5. 版式稳定：不同文本长度与数据量下是否溢出、遮挡或破坏层级。
6. 导出复验：生成后在实际演示软件中打开、编辑、放映和再次保存是否正常。
7. 原生对象深度：普通可编辑形状与数据驱动的 PowerPoint Chart/Table 不是同一级能力，应根据后续编辑需求选择并验收。
8. 动效行为：检查转场、逐元素进入/强调/退出动画的触发顺序、时间和可调性，不能只确认文件里“有动画”。
9. 返工安全：修改文字、模块数量、图表、配色和逻辑重点后，装饰元素和版式是否仍能自适应。
10. 交付路线：HTML 编辑态与 PPTX 交付态能力不同，应根据动画交互、协作兼容和原生编辑深度选择。

## 可复用生产流程

资料型演示文稿可采用“来源解析 → 叙事结构 → 设计规格确认 → 页面制作 → PPTX 导出 → PowerPoint 后验收”。快速模式可以减少确认，但不应取消事实检查、版式检查和最终文件复验。

PPT-Master 官方把生成、图片转 PPTX、美化、创建模板、填充原生模板和增强既有 PPTX 分为不同路线。可迁移的方法是先根据任务选择唯一工作流，再只加载该路线所需规则，避免混用多个生成路径造成约束冲突。

## 实现假设与边界

HTML 先行再转换为 PPTX 可能提高页面设计自由度，但转换后是否保持原生可编辑仍需实践验证。不能因为生成了 `.pptx` 文件就认定它满足编辑性要求。

PPT-Master 的官方资料与 4.8.0 工作流已经过来源环境核验；在接收者机器上仍需先检查是否安装、实际版本及依赖，确认后才可按任务描述自动匹配或显式调用。其 Python 依赖多数为分路线使用的可选依赖，实际调用时按选定路线检查并补齐。官方资料明确：工作流不等于质量保证，生成后仍需人工收尾，转场和逐元素动画仍应以目标 PowerPoint 文件实测为准。

Dashi PPT 官方仓库已经核验。它适合希望在浏览器控制台中修改布局、模块、图表、配色与页面重点，再导出 HTML/PDF/PPTX 的职场型场景；不适合逐像素自由定制。当前仓库要求 Node.js 20+，导出还需 Chrome/Chromium/Edge，并有 AGPL-3.0 与导出引擎专有许可边界。需要实际使用时，应先检查当前机器上 Dashi PPT 与 PPT-Master 的可用状态，再根据任务明确选择唯一工作流。

## CyberPPT 使用判断

- 官方仓库：<https://github.com/crazyykhllc-bit/CyberPPT>，MIT 许可。
- 适用：资料和数据充足、要求高信息密度、结论先行、咨询式论证、可审计证据链与可编辑 PPTX 的行业研究、高管汇报、董事会材料、客户提案或项目复盘。
- 不适用：低信息密度演讲、个人表达、纯叙事分享、只有观点而缺少来源材料，或任务无法承担逐阶段确认与逐页还原成本。
- 核心路线：证据表与缺口 → 2–3 条故事线和 SCR → 逐页密度/组件计划 → 8 张风格样张 → 全套 ImageGen 蓝图 → 逐页混合还原 → PowerPoint 渲染、manifest 与 strict QA。
- 可编辑性门：蓝图是视觉验收基准而不是最终背景；标题、正文、关键数字、简单图表、表格和 SO WHAT 默认应原生重建，复杂照片、Logo、插画或材质仅在必要时作为图片保留并登记影响。
- 使用时应把“结构可编辑”和“视觉还原”作为同等硬门槛。批量一次性还原容易造成注意力和信息密度漂移，复杂曲线、图标、字体和换行仍需逐页检查。
- 当前状态：官方 README 与 `SKILL.md` 已核验，来源机器未安装 `cyber-ppt`。接收者机器是否可调用必须重新检查；普通 PPT 任务可优先路由到本机已有能力，明确需要 CyberPPT 特有流程时再决定是否安装。
