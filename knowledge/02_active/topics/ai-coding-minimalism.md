# AI 编码的最小正确实现与过度工程门禁

## 当前认识

“少写代码”不是目标本身。更可靠的目标是在充分理解现有流程后，优先复用代码库、标准库、平台原生能力和已有依赖，只实现任务真正需要的最小正确方案，同时保留校验、安全、错误处理、可访问性和数据保护。

## 决策阶梯

1. 这个需求真的需要实现吗？
2. 代码库是否已经有可复用实现？
3. 标准库或平台原生能力是否足够？
4. 已安装依赖是否已经覆盖？
5. 仍需新增时，写最小可验证实现。

阶梯必须在读懂受影响代码、真实数据流和边界后执行，不能把 YAGNI 变成跳过分析。

## Ponytail 使用判断

- 官方仓库：<https://github.com/DietrichGebert/ponytail>
- 适用：边界明确的功能实现、差异审查、全仓库过度工程审计，以及容易误装依赖或过度抽象的前端/后端任务。
- 不适用：为了减少 LOC 删除安全门、错误处理、输入校验、无障碍或数据迁移保护；探索性原型也不应被迫提前收敛为最低变化度。
- 证据边界：官方代理基准平均为 LOC `-54%`、Tokens `-22%`、成本 `-20%`、时间 `-27%`；旧 `80%–94%` 是单轮代码量结果或个别任务上限，不能写成普遍 Token 降幅。
- 当前状态：运行时检查当前机器是否安装 Ponytail；未安装时只应用决策原则，不声称调用 Skill。用户明确要求安装后再按官方插件流程审查 hooks 与 Node 依赖。
